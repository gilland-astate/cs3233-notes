## 32.1 What Types Of Bugs Exist?
- **Concurrency Bugs**:
    - Issues that arise in multi-threaded or concurrent programs due to improper synchronization, resource sharing, or thread interactions.
    - Common in complex and mature codebases due to their scale and complexity.
### Study by Lu et al. 
- Analyzed concurrency bugs in four major open-source projects:
	1. **MySQL**: Database management system.
	2. **Apache**: Web server.
	3. **Mozilla**: Web browser.
	4. **OpenOffice**: Office suite.
- Focused on bugs found and fixed in these projects to provide insights into common concurrency issues.
#### Findings from the Study
- **105 Total Bugs**:
    - **Non-Deadlock Bugs**: 74
    - **Deadlock Bugs**: 31
- **Bug Distribution by Application**:
    - Mozilla: ~60 bugs.
    - Apache: ~30 bugs.
    - MySQL: ~7 bugs.
    - OpenOffice: ~8 bugs.

## 32.2 Non-Deadlock Bugs
- **Non-Deadlock Bugs**:    
    - Account for 70% of concurrency bugs studied by Lu et al.
    - Two major types:
        1. **Atomicity Violations**
        2. **Order Violations**
### Atomicity Violations
- **Definition**: Occurs when a sequence of operations intended to be atomic is interrupted, leading to incorrect results.
```c++
Thread 1::
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}

Thread 2::
thd->proc_info = NULL;
```
- **Problem**:
	- Thread 1 checks `proc_info` and finds it non-NULL.
	- Thread 1 is interrupted; Thread 2 sets `proc_info` to NULL.
	- Thread 1 resumes and dereferences a NULL pointer in `fputs()`, causing a crash.
- **Fix**: Use locks to ensure atomic access to shared resources.
```c++
pthread_mutex_t proc_info_lock = PTHREAD_MUTEX_INITIALIZER;

Thread 1::
pthread_mutex_lock(&proc_info_lock);
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}
pthread_mutex_unlock(&proc_info_lock);

Thread 2::
pthread_mutex_lock(&proc_info_lock);
thd->proc_info = NULL;
pthread_mutex_unlock(&proc_info_lock);
```
### Order Violations
- **Definition**: Occurs when the desired order between two (groups of) memory accesses is not enforced, resulting in incorrect behavior.
```c++
Thread 1::
void init() {
    mThread = PR_CreateThread(mMain, ...);
}

Thread 2::
void mMain(...) {
    mState = mThread->State;
}
```
- **Problem**:
	- If `Thread 2` runs before `Thread 1` has initialized `mThread`, it dereferences a NULL pointer, causing a crash.
- **Fix**: Use condition variables to enforce ordering.
```c++
pthread_mutex_t mtLock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t mtCond = PTHREAD_COND_INITIALIZER;
int mtInit = 0;

Thread 1::
void init() {
    mThread = PR_CreateThread(mMain, ...);

    pthread_mutex_lock(&mtLock);
    mtInit = 1;
    pthread_cond_signal(&mtCond);
    pthread_mutex_unlock(&mtLock);
}

Thread 2::
void mMain(...) {
    pthread_mutex_lock(&mtLock);
    while (mtInit == 0)
        pthread_cond_wait(&mtCond, &mtLock);
    pthread_mutex_unlock(&mtLock);

    mState = mThread->State;
}
```
### Patterns and Prevention
- **Atomicity Violations**:
    - Occur due to missing or incomplete locking.
    - Fix: Use locks to protect shared resources and ensure atomic operations.
- **Order Violations**:
    - Result from threads accessing resources in an incorrect sequence.
    - Fix: Use synchronization primitives like condition variables or semaphores to enforce proper order.
- **Key Insight**:
    - 97% of non-deadlock bugs are either atomicity or order violations.
    - Focus on these patterns can significantly improve concurrency safety.
### Lessons from Lu et al.
- **Automated Tools**: Should target atomicity and order violations to detect and prevent these bugs.
- **Best Practices**:
    - Always protect shared data with locks or synchronization primitives.
    - Use condition variables to enforce execution order when needed.
    - Test concurrency with stress tests to uncover hidden bugs.
- **Challenges**:
    - Fixes may require deeper understanding and significant refactoring in some cases.
    - Automated tools and careful design are critical to avoiding such bugs in practice.

## 32.3 Deadlock Bugs
- **Definition**: Deadlock occurs when two or more threads/processes are unable to proceed because they are waiting for resources held by each other.
- **Example**:
```c++
// Thread 1
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);

// Thread 2
pthread_mutex_lock(L2);
pthread_mutex_lock(L1);
```
* If Thread 1 acquires `L1` and Thread 2 acquires `L2`, both will wait indefinitely for the other to release their locks.
### Why Do Deadlocks Occur?
* **Complex Dependencies**: Circular dependencies arise in large systems like operating systems (e.g., virtual memory and file system interactions).
*  **Encapsulation Issues**: Modular design can hide critical locking details, making it difficult to enforce consistent locking protocols.
### Conditions for Deadlock (Coffman Conditions)
* Deadlock occurs when all the following conditions hold:
	1. **Mutual Exclusion**: Resources cannot be shared; only one thread can hold a resource at a time.
	2. **Hold-and-Wait**: Threads holding resources can request additional resources.
	3. **No Preemption**: Resources cannot be forcibly taken away.
	4. **Circular Wait**: A cycle of threads exists where each thread waits for a resource held by the next.
	* If any of these conditions are broken, deadlock cannot occur.
### Deadlock Handling Strategies
#### Deadlock Prevention
Prevention ensures one or more Coffman conditions cannot occur:
1. **Breaking Circular Wait**:
    - **Solution**: Impose an order on resource acquisition.
	* **Challenge**: Complex systems with multiple locks may require partial ordering.
```c++
pthread_mutex_lock(L1); // acquire L1 first
pthread_mutex_lock(L2); // acquire L2 next	
```
2. **Breaking Hold-and-Wait**:
    - **Solution**: Acquire all necessary locks atomically.
    - **Downside**: Reduces concurrency and increases complexity.
```c++
pthread_mutex_lock(prevention_lock);
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);
pthread_mutex_unlock(prevention_lock);
```
3. **Breaking No Preemption**:
    - **Solution**: Use `pthread_mutex_trylock()` to back out if a lock cannot be acquired.
	- **Risk**: Can lead to **livelock**, where threads continuously fail to acquire locks.
```c++
top:
pthread_mutex_lock(L1);
if (pthread_mutex_trylock(L2) != 0) {
    pthread_mutex_unlock(L1);
    goto top;
}
```
1. **Avoiding Mutual Exclusion**:
    - Use **lock-free data structures** and atomic operations.
    - **Challenge**: Complex to design and implement for general use.
```c++
void AtomicIncrement(int *value, int amount) {
    do {
        int old = *value;
    } while (CompareAndSwap(value, old, old + amount) == 0);
}
```
#### Deadlock Avoidance
Avoidance requires global knowledge of thread behavior and lock requirements:
1. **Static Scheduling**:
    - Analyze all threads' lock requirements and schedule them to avoid deadlock.
        - **Locks Needed**:
    
			| T1  | T2 | T3 | T4 |
			| --- | --- | --- | --- |
			| L1  | L1  | L2  | -   |
			| L2  | L2  | -    | -   |
            
        - **Schedule**:
            - CPU 1: T1 → T2
            - CPU 2: T3 → T4
		- As long as T1 and T2 are not run at the same time, no deadlock could ever arise. 
    - **Limitation**: Reduces concurrency and requires full knowledge of lock needs.
2. **Banker’s Algorithm**:
    - Dynamically allocate resources to avoid unsafe states.
    - Used in embedded systems or databases where resource needs are predictable.
#### Deadlock Detection and Recovery
1. **Detection**:
    - Periodically check for cycles in the **resource allocation graph** to identify deadlocks.
2. **Recovery**:
    - Restart affected processes or systems.
    - Database systems employ **deadlock detection** and restart transactions involved in a cycle.
