# Semaphores
## 31.1 Semaphores: A Definition
- **Definition**: A semaphore is an object with an integer value that can be manipulated using two main operations:
    1. `sem_wait()` – Decrement the semaphore value (waits if the value is negative).
    2. `sem_post()` – Increment the semaphore value (wakes a waiting thread if one exists).
- **Initialization**:
    - A semaphore must first be initialized using `sem_init()`.
```c++
sem_t s;
sem_init(&s, 0, 1); // 1 indicates initial semaphore value
```
* **Parameters for `sem_init()`**:
	1. Semaphore variable (`sem_t`).
	2. Sharing mode: `0` for thread synchronization within the same process.
	3. Initial value of the semaphore.
- **sem_wait()**:
    - Decrements the value of the semaphore.
    - If the value is **0 or less**, the calling thread suspends execution and waits for a `sem_post()` call to wake it up.
    - Multiple threads can call `sem_wait()` and queue up if they cannot proceed.
```c++
int sem_wait(sem_t *s) {
    decrement the value of semaphore s by one;
    wait if value of semaphore s is negative;
}
```
- **sem_post()**:
	- Increments the semaphore value.
	- If any threads are waiting, it wakes up one of them to continue execution.
```c++
int sem_post(sem_t *s) {
    increment the value of semaphore s by one;
    if there are one or more threads waiting, wake one;
}
```
- **Key Characteristics**:
	- **Atomicity**: Both `sem_wait()` and `sem_post()` execute atomically to prevent race conditions.
	- **Negative Semaphore Values**: If the semaphore value is negative, it indicates the number of threads waiting on the semaphore.
### Types of Semaphores
1. **Binary Semaphore (A Lock)**:
    - Used like a lock to provide mutual exclusion.
    - Initialized to `1`, so only one thread can decrement it to `0` and enter the critical section at a time.
    - After the critical section, `sem_post()` increments the semaphore to release the lock.
```c++
sem_t m;
sem_init(&m, 0, 1); // Binary semaphore initialized to 1

sem_wait(&m); // Acquires lock
// Critical section here
sem_post(&m); // Releases lock
```
2. **Counting Semaphore**:
	- Initialized to a value `X` to allow up to `X` threads to proceed concurrently.
	- Often used to control access to a limited number of resources.
```c++
sem_t m;
sem_init(&m, 0, 3); // Allow up to 3 threads

sem_wait(&m); // Decrements semaphore (resource acquired)
// Critical section here
sem_post(&m); // Increments semaphore (resource released)
```

### Uses of Semaphores
1. **Synchronization**: Ensure proper sequencing of thread execution (e.g., one thread must wait for another to finish before proceeding).
2. **Resource Management**: Limit the number of threads accessing a resource simultaneously (e.g., database connections or network sockets).
3. **Mutual Exclusion**: Implement locks using a binary semaphore.
### Semaphore vs. Other Synchronization Tools
- **Semaphores vs. Mutex**: A mutex is a binary semaphore with additional rules (e.g., only the thread that locked it can unlock it).
- **Semaphores vs. Condition Variables**: Condition variables are more suited for signaling threads to wake when specific conditions are met.

## 31.2 Binary Semaphores (Locks)
### Semaphores as Locks
- **Concept**: A semaphore can be used as a lock by surrounding a critical section with `sem_wait()` and `sem_post()` calls.
- **Initialization**: To use a semaphore as a lock, initialize its value to `1`. This ensures mutual exclusion, allowing only one thread to enter the critical section at a time.
### Behavior of Semaphores as Locks
- **Initial Value**: The semaphore's value starts at `1`.
- **Operation**:
    - **sem_wait()**:
        - Decrements the semaphore value.
        - If the value is `0` or greater, the thread continues execution.
        - If the value is less than `0`, the thread is put to sleep and waits for a `sem_post()` signal.
    - **sem_post()**:
        - Increments the semaphore value.
        - If one or more threads are waiting, it wakes one of them.
### Example Scenarios
1. **Single Thread Access**:
    - Thread 0 calls `sem_wait()`:
        - Decrements the semaphore value to `0` (lock acquired).
        - Enters the critical section.
    - Thread 0 calls `sem_post()`:
        - Increments the semaphore value back to `1` (lock released).

| Time | Semaphore Value | Thread 0 State                     |
| ---- | --------------- | ---------------------------------- |
| T1   | 1               | Calls `sem_wait()`                 |
| T2   | 0               | Enters critical section            |
| T3   | 1               | Calls `sem_post()` (lock released) |
2. **Two Threads with Contention**:
	- Thread 0 calls `sem_wait()` and enters the critical section.
	- Thread 1 calls `sem_wait()`:
	    - Decrements the semaphore value to `-1`.
	    - Goes to sleep, waiting for `sem_post()`.
	- Thread 0 calls `sem_post()`:
	    - Increments the semaphore value to `0`.
	    - Wakes up Thread 1, which then enters the critical section.

| Time | Semaphore Value | Thread 0 State                               | Thread 1 State                          |
| ---- | --------------- | -------------------------------------------- | --------------------------------------- |
| T1   | 1               | Calls `sem_wait()` (enters critical section) | Ready                                   |
| T2   | 0               | Critical section                             | Calls `sem_wait()` (value = -1, sleeps) |
| T3   | 0               | Calls `sem_post()` (wakes Thread 1)          | Sleeping                                |
| T4   | 0               | Exits                                        | Enters critical section                 |
3. **Multiple Waiting Threads**:
	- When multiple threads wait for a semaphore, the semaphore’s value goes negative, representing the number of waiting threads.
	- Each `sem_post()` call wakes one thread, incrementing the semaphore value toward `0`.

## 31.3 Semaphores For Ordering
- Semaphores can be used to order events in concurrent programs by signaling and waiting for conditions to be met.
- **Pattern**: One thread waits for an event (via `sem_wait()`), while another thread signals the event (via `sem_post()`).
### Example: Parent Waiting for Child Completion
- **Goal**: A parent thread waits for a child thread to complete before continuing execution.
- **Output Expected**:
```
parent: begin
child
parent: end
```
- **Implementation**:
	- The parent thread initializes a semaphore to `0`.
	- The parent calls `sem_wait()` to wait for the child to signal its completion.
	- The child thread calls `sem_post()` to signal the parent that it has finished.
```c++
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

sem_t s; // Semaphore

void *child(void *arg) {
    printf("child\n");
    sem_post(&s); // Signal the parent
    return NULL;
}

int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    sem_init(&s, 0, 0); // Initialize semaphore to 0

    pthread_t c;
    pthread_create(&c, NULL, child, NULL);

    sem_wait(&s); // Wait for the child to signal
    printf("parent: end\n");

    sem_destroy(&s);
    return 0;
}
```
### Behavior Analysis
- **Initial Semaphore Value**: `0`
    - Ensures the parent thread waits if the child has not signaled yet.
- **Case 1**: **Child Runs After Parent Waits**
    - Parent:
        1. Calls `sem_wait()`, decrementing semaphore to `-1`.
        2. Sleeps, waiting for the child.
    - Child:
        1. Runs and calls `sem_post()`, incrementing semaphore to `0`.
        2. Signals the parent, which wakes up and continues execution.

| Time | Semaphore Value | Parent State                    | Child State        |
| ---- | --------------- | ------------------------------- | ------------------ |
| T1   | 0               | Calls `sem_wait()` (value = -1) | Ready              |
| T2   | -1              | Waiting                         | Calls `sem_post()` |
| T3   | 0               | Continues                       | Exits              |

- **Case 2**: **Child Runs Before Parent Waits**    
    - Child:
        1. Runs and calls `sem_post()`, incrementing semaphore to `1`.
        2. Exits.
    - Parent:
        1. Calls `sem_wait()`, decrementing semaphore to `0`.
        2. Continues execution without waiting.

| Time | Semaphore Value | Parent State                   | Child State                    |
| ---- | --------------- | ------------------------------ | ------------------------------ |
| T1   | 0               | Ready                          | Calls `sem_post()` (value = 1) |
| T2   | 1               | Calls `sem_wait()` (value = 0) | Exits                          |
| T3   | 0               | Continues                      | -                              |

## 31.4 The Producer/Consumer (Bounded Buffer) Problem
- The **Producer/Consumer Problem** (or Bounded Buffer Problem) involves:
    - **Producers** adding data to a buffer.
    - **Consumers** removing data from the buffer.
- Goal: Synchronize access to the shared buffer, ensuring:
    1. Producers only add data to empty slots.
    2. Consumers only remove data from full slots.
    3. Avoid race conditions and deadlocks.
### Initial Solution with Semaphores
- **Semaphores Used**:
    - `empty`: Tracks the number of empty slots (initialized to `MAX`).
    - `full`: Tracks the number of filled slots (initialized to `0`).
```c++
sem_t empty, full;

void producer() {
    while (1) {
        sem_wait(&empty); // Wait for an empty slot
        buffer[fill] = produce_item(); // Add item to buffer
        fill = (fill + 1) % MAX;
        sem_post(&full); // Signal a full slot
    }
}

void consumer() {
    while (1) {
        sem_wait(&full); // Wait for a full slot
        item = buffer[use]; // Remove item from buffer
        use = (use + 1) % MAX;
        sem_post(&empty); // Signal an empty slot
        consume_item(item);
    }
}
```
### Observations and Issues
1. **For Single Buffer (MAX=1)**:
    - Works correctly as semaphores synchronize producer/consumer threads.
    - Semantics:
        - `sem_wait(&empty)`: Ensures the producer waits if no empty slots.
        - `sem_post(&full)`: Signals the consumer to proceed.
    - Behavior:
        - Producer/consumer alternate turns to avoid overwriting or consuming from an empty buffer.
2. **For Multiple Buffers (MAX > 1)**:
    - **Race Condition**:
        - Multiple producers/consumers may simultaneously access shared variables (`fill`, `use`) and overwrite data or cause errors.
    - Example:
        - Two producers access `fill` simultaneously, both write to the same buffer index, overwriting data.
### Adding Mutual Exclusion
- **Solution**:
    - Use a **binary semaphore (mutex)** to protect critical sections.
- **Initial Attempt**:
    - Lock the entire `put()` and `get()` routines.
```c++
sem_t mutex;

void put(int item) {
    sem_wait(&mutex);  // Acquire lock
    buffer[fill] = item;
    fill = (fill + 1) % MAX;
    sem_post(&mutex);  // Release lock
}

void get() {
    sem_wait(&mutex);  // Acquire lock
    item = buffer[use];
    use = (use + 1) % MAX;
    sem_post(&mutex);  // Release lock
}
```
### Deadlock Issue
- **Scenario**:
    - Consumer holds `mutex`, then calls `sem_wait(&full)` and blocks.
    - Producer tries to acquire `mutex`, but it's already held by the blocked consumer.
    - Both threads are stuck: **deadlock**.
### Final Working Solution
- **Fix**: Reduce the scope of the lock to only protect the critical section (buffer operations). Semaphore waits/signals (`sem_wait(&empty/full)`) are outside the critical section.
```c++
void producer() {
    while (1) {
        sem_wait(&empty);  // Wait for an empty slot
        sem_wait(&mutex);  // Lock critical section
        buffer[fill] = produce_item();
        fill = (fill + 1) % MAX;
        sem_post(&mutex);  // Unlock critical section
        sem_post(&full);   // Signal a full slot
    }
}

void consumer() {
    while (1) {
        sem_wait(&full);   // Wait for a full slot
        sem_wait(&mutex);  // Lock critical section
        item = buffer[use];
        use = (use + 1) % MAX;
        sem_post(&mutex);  // Unlock critical section
        sem_post(&empty);  // Signal an empty slot
        consume_item(item);
    }
}
```

## 31.5 Reader-Writer Locks
- **Problem**: Standard locks prevent any access (read or write) by multiple threads to shared data, even when reading can be done concurrently without conflicts.
- **Solution**: **Reader-Writer Lock** allows:
    - **Concurrent Reads**: Multiple readers can access the data simultaneously if no writers are active.
    - **Exclusive Writes**: Only one writer can access the data, blocking all readers and other writers.

### Key Components
- **Semaphores**:
    - `lock`: Protects access to the shared `readers` counter.
    - `writelock`: Ensures only one writer (or no readers) can access the critical section.
- **Reader Count**:
    - Tracks the number of active readers.
    - Helps manage when the `writelock` is acquired or released.
### Implementation
```c++
typedef struct _rwlock_t {
    sem_t lock;         // Binary semaphore for readers
    sem_t writelock;    // Semaphore for writers
    int readers;        // Number of active readers
} rwlock_t;

void rwlock_init(rwlock_t *rw) {
    rw->readers = 0;
    sem_init(&rw->lock, 0, 1);      // Initialize binary semaphore
    sem_init(&rw->writelock, 0, 1); // Initialize writer semaphore
}

void rwlock_acquire_readlock(rwlock_t *rw) {
    sem_wait(&rw->lock);            // Synchronize access to readers
    rw->readers++;
    if (rw->readers == 1)           // First reader locks writers
        sem_wait(&rw->writelock);
    sem_post(&rw->lock);            // Release reader lock
}

void rwlock_release_readlock(rwlock_t *rw) {
    sem_wait(&rw->lock);            // Synchronize access to readers
    rw->readers--;
    if (rw->readers == 0)           // Last reader unlocks writers
        sem_post(&rw->writelock);
    sem_post(&rw->lock);            // Release reader lock
}

void rwlock_acquire_writelock(rwlock_t *rw) {
    sem_wait(&rw->writelock);       // Ensure mutual exclusion for writers
}

void rwlock_release_writelock(rwlock_t *rw) {
    sem_post(&rw->writelock);       // Allow others to acquire write lock
}
```
### Limitations
1. **Reader Starvation**: Readers can starve writers if new readers continuously acquire the read lock.
2. **Fairness**: Implementation does not prioritize waiting writers, potentially delaying their execution indefinitely.
3. **Overhead**: Managing multiple semaphores and counters can introduce performance overhead in low-contention scenarios.

## 
- **Setup**:
    - Five philosophers sit around a table with five forks.
    - Each philosopher alternates between **thinking** and **eating**.
    - To eat, a philosopher needs **two forks**: one on their left and one on their right.
- **Goal**: Solve synchronization issues so:
	1. **No Deadlock**: Philosophers must not get stuck waiting indefinitely for forks.
	2. **No Starvation**: Every philosopher gets to eat eventually.
	3. **High Concurrency**: Maximize the number of philosophers eating simultaneously.

```c++
sem_t forks[5];

int left(int p) { return p; }                // Left fork index
int right(int p) { return (p + 1) % 5; }    // Right fork index

while (1) {
    think();              // Think for some time
    get_forks(p);         // Acquire both forks
    eat();                // Eat when both forks are acquired
    put_forks(p);         // Release the forks
}
```

### First (Broken) Solution
```c++
void get_forks(int p) {
    sem_wait(&forks[left(p)]);   // Acquire left fork
    sem_wait(&forks[right(p)]); // Acquire right fork
}

void put_forks(int p) {
    sem_post(&forks[left(p)]);   // Release left fork
    sem_post(&forks[right(p)]); // Release right fork
}
```
**Issue**: **Deadlock**
- If each philosopher grabs the fork on their left simultaneously, no forks will be available for the right hand.
- This creates a circular wait condition, leading to deadlock.
### Solution: Breaking the Dependency
- **Idea**: Change the order in which forks are acquired for one philosopher to break the circular dependency.
```c++
void get_forks(int p) {
    if (p == 4) {  // Philosopher 4 grabs forks in reverse order
        sem_wait(&forks[right(p)]);
        sem_wait(&forks[left(p)]);
    } else {       // Other philosophers grab left first, then right
        sem_wait(&forks[left(p)]);
        sem_wait(&forks[right(p)]);
    }
}
```
* **Effect**:
	- Philosopher 4 grabs the **right fork first**, breaking the cycle of waiting.
	- This ensures deadlock cannot occur.
### Key Considerations
- **Fairness**: The above solution ensures no philosopher gets stuck forever, provided all philosophers follow the protocol.
- **Concurrency**: The solution allows up to two non-adjacent philosophers to eat simultaneously.
### Other famous concurrency problems
- **Cigarette Smoker's Problem**: Models resource allocation with multiple dependencies.
- **Sleeping Barber Problem**: Focuses on producer-consumer synchronization.

##
- **Challenge**:
    - Prevent “too many” threads from executing a specific section of code simultaneously.
    - Avoid overloading system resources, which could lead to inefficiency (e.g., memory thrashing, high CPU contention).
- **Solution**:
    - Use a **semaphore** to limit the number of threads concurrently entering the critical section.
    - This technique is known as **throttling** or **admission control**.
### Key Concepts
- **Threshold for Concurrency**:
    - Define a maximum number of threads that can execute the code at once.
    - Any threads exceeding this limit must wait.
- **Semaphores**:
    - Initialize the semaphore value to the threshold.
    - Use `sem_wait()` to decrement and check if a thread can proceed.
    - Use `sem_post()` to increment the semaphore value when a thread exits the critical section.
### Example Use Case: Memory-Intensive Region
- **Scenario**:
    - Multiple threads perform computations in parallel.
    - A **memory-intensive region** in the code allocates large memory blocks for processing.
    - If too many threads enter the memory-intensive region, the system can run out of physical memory, causing **thrashing**.
- **Solution**:
    - Use a semaphore to limit the number of threads in the memory-intensive region.
```c++
#include <semaphore.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>

#define MAX_THREADS 4  // Maximum threads allowed in memory-intensive region

sem_t throttle;  // Semaphore to control access

void memory_intensive_region(int thread_id) {
    printf("Thread %d: Entering memory-intensive region\n", thread_id);
    // Simulate memory-intensive work
    sleep(2);  
    printf("Thread %d: Leaving memory-intensive region\n", thread_id);
}

void *thread_function(void *arg) {
    int thread_id = *(int *)arg;

    // Throttling using semaphore
    sem_wait(&throttle);  // Wait until allowed to enter
    memory_intensive_region(thread_id);  // Critical section
    sem_post(&throttle);  // Signal that region is free

    free(arg);
    return NULL;
}

int main() {
    pthread_t threads[10];  // Assume 10 threads
    sem_init(&throttle, 0, MAX_THREADS);  // Initialize semaphore to MAX_THREADS

    // Create threads
    for (int i = 0; i < 10; i++) {
        int *thread_id = malloc(sizeof(int));
        *thread_id = i;
        pthread_create(&threads[i], NULL, thread_function, thread_id);
    }

    // Wait for threads to complete
    for (int i = 0; i < 10; i++) {
        pthread_join(threads[i], NULL);
    }

    sem_destroy(&throttle);  // Clean up semaphore
    return 0;
}
```
- **Initialization**:
    - `sem_init(&throttle, 0, MAX_THREADS)` sets the semaphore to the threshold value.
- **Critical Section**:
    - Threads entering the memory-intensive region call `sem_wait(&throttle)`, decrementing the semaphore.
    - If the semaphore value is zero, the thread waits until another thread exits the region and calls `sem_post(&throttle)`.
- **Concurrency Control**:
    - At most `MAX_THREADS` threads can execute the critical section concurrently.
### Key Considerations
- **Advantages**:
    - Simple implementation with a semaphore.
    - Effectively prevents system overload by limiting concurrent threads in the critical region.
- **Limitations**: Threads waiting for the semaphore may experience delays, reducing parallelism.
- **Scalability**: Adjust the semaphore value to balance resource usage and performance.
### Real-World Applications
- **Resource Throttling**: Limiting the number of threads accessing a database or network resource.
- **Memory Management**: Preventing out-of-memory errors in multi-threaded applications with high memory demands.
- **CPU Control**: Reducing contention in CPU-bound tasks by limiting concurrent thread execution.
