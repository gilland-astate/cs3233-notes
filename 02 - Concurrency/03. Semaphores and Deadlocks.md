# Semaphores
## 31.1 Semaphores: A Definition
- **Definition**: A semaphore is an object with an integer value that can be manipulated using two main operations:
    1. `sem_wait()` – Decrement the semaphore value (waits if the value is negative).
    2. `sem_post()` – Increment the semaphore value (wakes a waiting thread if one exists).
- **Initialization**:
    - A semaphore must first be initialized using `sem_init()`.
```c++
sem_t s;
sem_init(&s, 0, 1); // 1 indicates initial semaphore value
```
* **Parameters for `sem_init()`**:
	1. Semaphore variable (`sem_t`).
	2. Sharing mode: `0` for thread synchronization within the same process.
	3. Initial value of the semaphore.
- **sem_wait()**:
    - Decrements the value of the semaphore.
    - If the value is **0 or less**, the calling thread suspends execution and waits for a `sem_post()` call to wake it up.
    - Multiple threads can call `sem_wait()` and queue up if they cannot proceed.
```c++
int sem_wait(sem_t *s) {
    decrement the value of semaphore s by one;
    wait if value of semaphore s is negative;
}
```
- **sem_post()**:
	- Increments the semaphore value.
	- If any threads are waiting, it wakes up one of them to continue execution.
```c++
int sem_post(sem_t *s) {
    increment the value of semaphore s by one;
    if there are one or more threads waiting, wake one;
}
```
- **Key Characteristics**:
	- **Atomicity**: Both `sem_wait()` and `sem_post()` execute atomically to prevent race conditions.
	- **Negative Semaphore Values**: If the semaphore value is negative, it indicates the number of threads waiting on the semaphore.
### Types of Semaphores
1. **Binary Semaphore (A Lock)**:
    - Used like a lock to provide mutual exclusion.
    - Initialized to `1`, so only one thread can decrement it to `0` and enter the critical section at a time.
    - After the critical section, `sem_post()` increments the semaphore to release the lock.
```c++
sem_t m;
sem_init(&m, 0, 1); // Binary semaphore initialized to 1

sem_wait(&m); // Acquires lock
// Critical section here
sem_post(&m); // Releases lock
```
2. **Counting Semaphore**:
	- Initialized to a value `X` to allow up to `X` threads to proceed concurrently.
	- Often used to control access to a limited number of resources.
```c++
sem_t m;
sem_init(&m, 0, 3); // Allow up to 3 threads

sem_wait(&m); // Decrements semaphore (resource acquired)
// Critical section here
sem_post(&m); // Increments semaphore (resource released)
```

### Uses of Semaphores
1. **Synchronization**: Ensure proper sequencing of thread execution (e.g., one thread must wait for another to finish before proceeding).
2. **Resource Management**: Limit the number of threads accessing a resource simultaneously (e.g., database connections or network sockets).
3. **Mutual Exclusion**: Implement locks using a binary semaphore.
### Semaphore vs. Other Synchronization Tools
- **Semaphores vs. Mutex**: A mutex is a binary semaphore with additional rules (e.g., only the thread that locked it can unlock it).
- **Semaphores vs. Condition Variables**: Condition variables are more suited for signaling threads to wake when specific conditions are met.

## 31.2 Binary Semaphores (Locks)
### Semaphores as Locks
- **Concept**: A semaphore can be used as a lock by surrounding a critical section with `sem_wait()` and `sem_post()` calls.
- **Initialization**: To use a semaphore as a lock, initialize its value to `1`. This ensures mutual exclusion, allowing only one thread to enter the critical section at a time.
### Behavior of Semaphores as Locks
- **Initial Value**: The semaphore's value starts at `1`.
- **Operation**:
    - **sem_wait()**:
        - Decrements the semaphore value.
        - If the value is `0` or greater, the thread continues execution.
        - If the value is less than `0`, the thread is put to sleep and waits for a `sem_post()` signal.
    - **sem_post()**:
        - Increments the semaphore value.
        - If one or more threads are waiting, it wakes one of them.
### Example Scenarios
1. **Single Thread Access**:
    - Thread 0 calls `sem_wait()`:
        - Decrements the semaphore value to `0` (lock acquired).
        - Enters the critical section.
    - Thread 0 calls `sem_post()`:
        - Increments the semaphore value back to `1` (lock released).

| Time | Semaphore Value | Thread 0 State                     |
| ---- | --------------- | ---------------------------------- |
| T1   | 1               | Calls `sem_wait()`                 |
| T2   | 0               | Enters critical section            |
| T3   | 1               | Calls `sem_post()` (lock released) |
2. **Two Threads with Contention**:
	- Thread 0 calls `sem_wait()` and enters the critical section.
	- Thread 1 calls `sem_wait()`:
	    - Decrements the semaphore value to `-1`.
	    - Goes to sleep, waiting for `sem_post()`.
	- Thread 0 calls `sem_post()`:
	    - Increments the semaphore value to `0`.
	    - Wakes up Thread 1, which then enters the critical section.

| Time | Semaphore Value | Thread 0 State                               | Thread 1 State                          |
| ---- | --------------- | -------------------------------------------- | --------------------------------------- |
| T1   | 1               | Calls `sem_wait()` (enters critical section) | Ready                                   |
| T2   | 0               | Critical section                             | Calls `sem_wait()` (value = -1, sleeps) |
| T3   | 0               | Calls `sem_post()` (wakes Thread 1)          | Sleeping                                |
| T4   | 0               | Exits                                        | Enters critical section                 |
3. **Multiple Waiting Threads**:
	- When multiple threads wait for a semaphore, the semaphore’s value goes negative, representing the number of waiting threads.
	- Each `sem_post()` call wakes one thread, incrementing the semaphore value toward `0`.

## 31.3 Semaphores For Ordering
- Semaphores can be used to order events in concurrent programs by signaling and waiting for conditions to be met.
- **Pattern**: One thread waits for an event (via `sem_wait()`), while another thread signals the event (via `sem_post()`).
### Example: Parent Waiting for Child Completion
- **Goal**: A parent thread waits for a child thread to complete before continuing execution.
- **Output Expected**:
```
parent: begin
child
parent: end
```
- **Implementation**:
	- The parent thread initializes a semaphore to `0`.
	- The parent calls `sem_wait()` to wait for the child to signal its completion.
	- The child thread calls `sem_post()` to signal the parent that it has finished.
```c++
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

sem_t s; // Semaphore

void *child(void *arg) {
    printf("child\n");
    sem_post(&s); // Signal the parent
    return NULL;
}

int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    sem_init(&s, 0, 0); // Initialize semaphore to 0

    pthread_t c;
    pthread_create(&c, NULL, child, NULL);

    sem_wait(&s); // Wait for the child to signal
    printf("parent: end\n");

    sem_destroy(&s);
    return 0;
}
```
### Behavior Analysis
- **Initial Semaphore Value**: `0`
    - Ensures the parent thread waits if the child has not signaled yet.
- **Case 1**: **Child Runs After Parent Waits**
    - Parent:
        1. Calls `sem_wait()`, decrementing semaphore to `-1`.
        2. Sleeps, waiting for the child.
    - Child:
        1. Runs and calls `sem_post()`, incrementing semaphore to `0`.
        2. Signals the parent, which wakes up and continues execution.

| Time | Semaphore Value | Parent State                    | Child State        |
| ---- | --------------- | ------------------------------- | ------------------ |
| T1   | 0               | Calls `sem_wait()` (value = -1) | Ready              |
| T2   | -1              | Waiting                         | Calls `sem_post()` |
| T3   | 0               | Continues                       | Exits              |

- **Case 2**: **Child Runs Before Parent Waits**    
    - Child:
        1. Runs and calls `sem_post()`, incrementing semaphore to `1`.
        2. Exits.
    - Parent:
        1. Calls `sem_wait()`, decrementing semaphore to `0`.
        2. Continues execution without waiting.

| Time | Semaphore Value | Parent State                   | Child State                    |
| ---- | --------------- | ------------------------------ | ------------------------------ |
| T1   | 0               | Ready                          | Calls `sem_post()` (value = 1) |
| T2   | 1               | Calls `sem_wait()` (value = 0) | Exits                          |
| T3   | 0               | Continues                      | -                              |

## 31.4 The Producer/Consumer (Bounded Buffer) Problem
- The **Producer/Consumer Problem** (or Bounded Buffer Problem) involves:
    - **Producers** adding data to a buffer.
    - **Consumers** removing data from the buffer.
- Goal: Synchronize access to the shared buffer, ensuring:
    1. Producers only add data to empty slots.
    2. Consumers only remove data from full slots.
    3. Avoid race conditions and deadlocks.
### Initial Solution with Semaphores
- **Semaphores Used**:
    - `empty`: Tracks the number of empty slots (initialized to `MAX`).
    - `full`: Tracks the number of filled slots (initialized to `0`).
```c++
sem_t empty, full;

void producer() {
    while (1) {
        sem_wait(&empty); // Wait for an empty slot
        buffer[fill] = produce_item(); // Add item to buffer
        fill = (fill + 1) % MAX;
        sem_post(&full); // Signal a full slot
    }
}

void consumer() {
    while (1) {
        sem_wait(&full); // Wait for a full slot
        item = buffer[use]; // Remove item from buffer
        use = (use + 1) % MAX;
        sem_post(&empty); // Signal an empty slot
        consume_item(item);
    }
}
```
### Observations and Issues
1. **For Single Buffer (MAX=1)**:
    - Works correctly as semaphores synchronize producer/consumer threads.
    - Semantics:
        - `sem_wait(&empty)`: Ensures the producer waits if no empty slots.
        - `sem_post(&full)`: Signals the consumer to proceed.
    - Behavior:
        - Producer/consumer alternate turns to avoid overwriting or consuming from an empty buffer.
2. **For Multiple Buffers (MAX > 1)**:
    - **Race Condition**:
        - Multiple producers/consumers may simultaneously access shared variables (`fill`, `use`) and overwrite data or cause errors.
    - Example:
        - Two producers access `fill` simultaneously, both write to the same buffer index, overwriting data.
### Adding Mutual Exclusion
- **Solution**:
    - Use a **binary semaphore (mutex)** to protect critical sections.
- **Initial Attempt**:
    - Lock the entire `put()` and `get()` routines.
```c++
sem_t mutex;

void put(int item) {
    sem_wait(&mutex);  // Acquire lock
    buffer[fill] = item;
    fill = (fill + 1) % MAX;
    sem_post(&mutex);  // Release lock
}

void get() {
    sem_wait(&mutex);  // Acquire lock
    item = buffer[use];
    use = (use + 1) % MAX;
    sem_post(&mutex);  // Release lock
}
```
### Deadlock Issue
- **Scenario**:
    - Consumer holds `mutex`, then calls `sem_wait(&full)` and blocks.
    - Producer tries to acquire `mutex`, but it's already held by the blocked consumer.
    - Both threads are stuck: **deadlock**.
### Final Working Solution
- **Fix**: Reduce the scope of the lock to only protect the critical section (buffer operations). Semaphore waits/signals (`sem_wait(&empty/full)`) are outside the critical section.
```c++
void producer() {
    while (1) {
        sem_wait(&empty);  // Wait for an empty slot
        sem_wait(&mutex);  // Lock critical section
        buffer[fill] = produce_item();
        fill = (fill + 1) % MAX;
        sem_post(&mutex);  // Unlock critical section
        sem_post(&full);   // Signal a full slot
    }
}

void consumer() {
    while (1) {
        sem_wait(&full);   // Wait for a full slot
        sem_wait(&mutex);  // Lock critical section
        item = buffer[use];
        use = (use + 1) % MAX;
        sem_post(&mutex);  // Unlock critical section
        sem_post(&empty);  // Signal an empty slot
        consume_item(item);
    }
}
```
