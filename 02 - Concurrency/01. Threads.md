# Concurrency: An Introduction
### Threads as an OS Abstraction
- Threads introduce a new abstraction for execution within a program.
- Unlike a single-threaded process that has one execution point (a single program counter), a **multi-threaded program** has multiple points of execution, each managed by a separate thread.
- **Threads share the same address space** and can access the same data, differentiating them from separate processes that each have their own address space.
### Thread State and Context Switching
- Each thread has its own **program counter (PC)** and **set of registers** for computation.
- Context switching between threads involves saving the state of one thread and restoring the state of another, similar to **process context switching**, but without changing the address space or page table.
- Threads are managed using **thread control blocks (TCBs)**, akin to process control blocks (PCBs) used for processes.
### Stacks in Multi-Threaded Processes
- In a **single-threaded process**, there is typically one stack that resides at the bottom of the address space.
- In a **multi-threaded process**, each thread has its own **separate stack** for storing local variables, parameters, and return addresses (known as **thread-local storage**).
- The address space of a multi-threaded process contains **multiple stacks**, which can be spread throughout the space.
### Implications of Multi-Threaded Stacks
- The classic address space layout, with a single growing stack and heap, becomes more complex with multiple stacks present.
- Stacks in multi-threaded programs need not be large, as they typically handle routine-level data unless heavy recursion is involved.
### Key Differences Between Threads and Processes
- Threads share the **same address space**, unlike processes that have separate address spaces.
- A **context switch between threads** does not require changing the memory context, unlike process context switches that involve changing the page table.

## 26.1 Why Use Threads?
- Threads provide a way to have multiple points of execution within a single program, sharing the same address space.
- Threads can be used to parallelize tasks and overlap I/O operations with computation, improving the performance and responsiveness of programs.
### Key Reasons to Use Threads
#### Parallelism
- Threads can be used to speed up programs by dividing tasks across multiple processors.
- Example: Operations on large arrays can be divided so each processor performs a portion of the work.
- The process of adapting a single-threaded program to run on multiple CPUs is called **parallelization**.
#### Non-Blocking Progress
- Threads help avoid program stalling due to slow I/O operations (e.g., waiting for disk I/O, network messages, or page faults).
- When one thread is blocked waiting for I/O, the CPU scheduler can switch to other threads that are ready to run.
- This enables overlapping of I/O and computation within a single program, akin to how **multiprogramming** works across different processes.
### Threads vs. Processes
- Threads are preferable when tasks need to share data and use the same address space, simplifying data sharing within a program.
- Processes are better suited for logically distinct tasks that do not need to share memory, ensuring better isolation.
#### Applications of Threading
- Modern server-based applications, such as **web servers** and **database management systems**, commonly use threads to handle concurrent requests efficiently.
- Threads allow for more responsive programs, capable of handling multiple tasks without stalling due to waiting for I/O.

## 26.2 An Example: Thread Creation
- A program can create multiple threads that run concurrently.
- Threads run independently and can execute functions simultaneously or in different sequences, depending on the OS scheduler.
- Example code (Figure 26.2) demonstrates a main program that creates two threads (T1 and T2), which run a function `mythread()` with different arguments (e.g., printing “A” or “B”).
### Behavior of Threads
#### Main Thread and Thread Join
- The main thread creates T1 and T2 and then calls `pthread_join()` twice to wait for each thread to complete before continuing its own execution.
- This ensures that the main thread waits for the completion of T1 and T2 before printing "main: end" and exiting.
#### Thread Execution Ordering
- Threads can start running immediately after creation or may remain in a "ready" state until scheduled to run.
- The execution order is not predetermined and can vary based on the scheduler’s decisions.
### Possible Execution Orders
- **Sequential Execution**: Threads T1 and T2 may run in the order they were created, producing output such as "A" followed by "B".
- **Concurrent Execution**: Threads may run concurrently, especially on multiprocessor systems, resulting in interleaved or simultaneous outputs.
- **Reverse Order**:
	- The scheduler might choose to run T2 before T1, leading to "B" being printed before "A".
	- Execution is unpredictable, as shown in Figures 26.3, 26.4, and 26.5, with different scheduling scenarios.
### Thread Creation vs. Function Call
- Creating a thread is like calling a function, but instead of executing sequentially and returning control to the caller, a new thread of execution is started.
- Threads operate independently and may run before or after returning from the `pthread_create()` call.
### Implications of Thread Scheduling
- The OS scheduler controls which thread runs at any moment, implementing a scheduling algorithm that affects the order of execution.
- Predicting the exact sequence of execution can be challenging due to the scheduler's dynamic decisions.
#### Concurrency Complexity
- Understanding and predicting the behavior of programs with concurrent threads is complex, as it is difficult to anticipate which thread will run when.
- This complexity makes concurrent programming more challenging than single-threaded programming.

## 26.3 Why It Gets Worse: Shared Data
- In multi-threaded programs, threads often need to access and modify shared data. This introduces potential issues if not handled correctly.
- Example scenario: two threads updating a global shared variable (`counter`).
### Code Structure and Example
- **Thread Creation**: The program creates two threads that each run the same function but with different identifiers (e.g., “A” and “B”).
- **Shared Variable Update**: Each thread increments a shared counter variable in a loop (e.g., 10 million times each). The expected outcome for the `counter` should be 20 million after both threads finish execution.
### Expected vs. Actual Behavior
- **Expected Outcome**: In an ideal scenario, where threads execute without any conflicts or data races, the final output should be `counter = 20,000,000`.
- **Observed Outcomes**: When the program is compiled and executed, it often does not produce the expected result. Example outcomes may show:
		- `counter = 19,345,221`
		- `counter = 19,221,041`
	- Different runs can yield different, incorrect results.
### Understanding the Problem
- **Non-Deterministic Results**: The results differ across runs, highlighting non-deterministic behavior. This can be surprising as computers are expected to produce consistent, deterministic results.
- **Race Conditions**: Where multiple threads access and modify shared data concurrently without proper synchronization.
	- A race condition occurs when the outcome of a program depends on the non-deterministic timing of thread execution.
- **Thread Interleaving**: The problem arises from the way thread execution is interleaved. Without synchronization, two threads may read and modify `counter` at the same time, leading to inconsistent updates.
### Why It Happens
- **Atomicity Violation**:
	- Operations like reading, incrementing, and writing to `counter` are not atomic. The sequence:
		1. Thread A reads `counter`.
		2. Thread B reads `counter`.
		3. Thread A increments and writes to `counter`.
		4. Thread B increments and writes to `counter`.
	- This results in one increment being lost, as both threads read the same initial value.
- **Concurrent Access**: The CPU scheduler can switch between threads at any time, causing these atomic operations to interleave unpredictably.
### Determinism vs. Concurrency
- **Deterministic Programs**: Single-threaded programs generally behave deterministically, producing the same result every run.
- **Concurrent Programs**: Multi-threaded programs can behave non-deterministically due to concurrency, where the exact sequence of thread execution may change across runs.

## 26.4 The Heart Of The Problem: Uncontrolled Scheduling
- To understand race conditions, consider the code sequence generated by a compiler for incrementing a shared variable (`counter`):
```c++
mov 0x8049a1c, %eax   // Load the value of counter into register eax
add $0x1, %eax        // Increment the value in eax by 1
mov %eax, 0x8049a1c   // Store the updated value back into counter
```
- In this sequence, the `mov` instruction loads the memory value into a register, the `add` instruction increments it, and the final `mov` stores the new value back to memory.
### Thread Execution and Context Switching
- Assume two threads, Thread 1 and Thread 2, run this code concurrently:
    - **Thread 1** loads `counter` (initially 50) into `eax`, increments it to 51, and is preempted by a context switch.
    - **Thread 2** runs the same sequence, loading `counter` (still 50), incrementing to 51, and storing it.
    - **Thread 1** resumes, and stores its value (51) into `counter`.
- **Final result**: Despite both threads running the increment code, `counter` is only incremented to 51 instead of 52.
### Detailed Execution Trace
- The following is a simplified trace illustrating the problem:
| Step|Thread|Instruction|`counter` Value|
|---|---|---|---|
|1|1|`mov`|50|
|2|1|`add`|-|
|3||**Context Switch**|-|
|4|2|`mov`|50|
|5|2|`add`|-|
|6|2|`mov` (store)|51|
|7||**Context Switch**|-|
|8|1|`mov` (store)|51|
### Race Condition and Indeterminate Results
- A **race condition** occurs when the outcome of the program depends on the timing of thread execution.
- The issue here is that multiple threads access and modify shared data (`counter`) without proper coordination, leading to non-deterministic results.
- This results in **indeterminate behavior**, where the output varies between runs.
### Critical Sections and Mutual Exclusion
- A **critical section** is a part of code that accesses shared resources and should not be executed by more than one thread at a time.
- The goal is to achieve **mutual exclusion**, ensuring that only one thread can execute in the critical section at any given moment.
### Historical Context
- The terms related to concurrency, such as race conditions, critical sections, and mutual exclusion, were coined by Edsger Dijkstra in his influential 1968 paper, "Cooperating Sequential Processes."
- Dijkstra’s work laid the foundation for understanding and addressing concurrency issues in computing.

## 26.5 The Wish For Atomicity
- **Definition**: An atomic operation is one that runs to completion without any possibility of interruption. This guarantees that the operation is executed as a single, indivisible step.
- **Example**: A hypothetical `memory-add` instruction could look like:
```c++
memory-add 0x8049a1c, $0x1
```
This instruction would add 1 to the memory location `0x8049a1c` in a single step, ensuring that no other thread can modify the value during its execution.
### Why Atomicity Matters
- **Prevents Race Conditions**: Ensures that shared variables are updated correctly, even when multiple threads attempt to modify them simultaneously.
- **Guarantee**: Hardware ensures that an atomic instruction, once started, will either complete entirely or not at all, preventing partial execution states.
### Challenges with Atomic Operations
- **Limited Use**: Atomic instructions are practical for simple operations, such as incrementing a variable or swapping values.
- **Complexity with Larger Tasks**: Implementing atomic instructions for more complex operations (e.g., updating data structures like trees or lists) is impractical. The hardware cannot realistically support specialized instructions for every possible complex operation.
### Synchronization Primitives
- **Purpose**: To build mechanisms that ensure threads access shared resources safely, avoiding race conditions and ensuring mutual exclusion.
- **Basic Primitives**:
    - **Test-and-Set**: Checks and sets a variable in one atomic action, often used for simple lock implementations.
    - **Compare-and-Swap (CAS)**: Compares a memory location’s current value with an expected value and updates it if they match, enabling lock-free data structures.
- **Usage**: These primitives serve as building blocks for higher-level synchronization tools, like **mutexes**, **semaphores**, and **spinlocks**, which provide structured ways to manage access to critical sections.

## 26.6 One More Problem: Waiting For Another
- **Common Perspective**: Initially, concurrency problems are often discussed in the context of threads accessing shared variables, emphasizing the need for atomic operations to ensure correct behavior in critical sections.
- **Beyond Atomicity**: There is another significant type of thread interaction that requires attention: situations where one thread must wait for another to complete an action before proceeding.
### Thread Dependencies
- **Example Scenario**: This interaction is common in processes involving I/O operations. For instance, when a process requests disk I/O, it may be put to sleep while waiting. Once the I/O operation completes, the thread must be signaled to wake up and continue its work.
- **Significance**: This behavior introduces the need for synchronization mechanisms that handle sleeping and waking up threads, ensuring threads can properly coordinate and signal each other for seamless execution.
### Synchronization Mechanisms Overview
- **Atomicity Support**: Mechanisms like locks, semaphores, and atomic operations ensure only one thread accesses critical sections at a time.
- **Thread Coordination**: New synchronization tools are needed to manage dependencies where threads wait for specific conditions to be met by other threads before resuming execution.
- **Condition Variables**: These will be explored in detail to understand how they enable threads to wait for certain conditions and how signals can wake them up once those conditions are satisfied.
- **Sleeping and Waking Patterns**: The concept of putting a thread to sleep until it is explicitly awakened is crucial for building robust multi-threaded programs that handle waiting and signaling properly.
	
	**ASIDE: KEY CONCURRENCY TERMS 
	CRITICAL SECTION, RACE CONDITION, INDETERMINATE, MUTUAL EXCLUSION**
	These four terms are so central to concurrent code that we thought it worth while to call them out explicitly. See some of Dijkstra’s early work for more details.
	- A critical section is a piece of code that accesses a shared resource, usually a variable or data structure.
	- A race condition (or data race [NM92]) arises if multiple threads of execution enter the critical section at roughly the same time; both attempt to update the shared data structure, leading to a surprising (and perhaps undesirable) outcome.
	* An indeterminate program consists of one or more race conditions; the output of the program varies from run to run, depending on which threads ran when. The outcome is thus not deterministic, something we usually expect from computer systems.
	* To avoid these problems, threads should use some kind of mutual exclusion primitives; doing so guarantees that only a single thread ever enters a critical section, thus avoiding races, and resulting in deterministic program outputs.

# Locks
##  28.1 Locks: The Basic Idea
- **Locks** are synchronization mechanisms used to control access to **critical sections**—parts of the code that modify shared resources and must not be concurrently accessed by multiple threads.
- **Example Critical Section**: Updating a shared variable, such as `balance = balance + 1;`, which could lead to inconsistent values if multiple threads try to perform this update at the same time.
### Using Locks in Code
- **Lock Declaration**: A lock variable (e.g., `mutex`) must be declared globally or in a shared space to be accessible to all threads needing access to the critical section.
#### Lock/Unlock Mechanism
- **Acquire Lock**: Call `lock(&mutex);` before entering the critical section. If the lock is free (not held by another thread), the thread acquires the lock and becomes the "owner."
- **Release Lock**: Call `unlock(&mutex);` after completing the critical section. This makes the lock available for other threads.
```c++
lock_t mutex; // declare a lock variable
...
lock(&mutex);       // acquire lock
balance = balance + 1; // critical section
unlock(&mutex);     // release lock
```
### Lock States
- **Available/Free**: No thread holds the lock, so any thread can acquire it.
- **Acquired/Held**: One thread holds the lock and is in the critical section; other threads trying to acquire the lock must wait until it’s released.
### Behavior of Lock() and Unlock()
#### lock() Function
- When a thread calls `lock()`, it attempts to acquire the lock. If the lock is free, the thread acquires it and enters the critical section.
- If the lock is already held by another thread, the calling thread will wait (block) until the lock becomes available.
#### unlock() Function
- The current owner of the lock calls `unlock()` to release it after exiting the critical section.
- If other threads are waiting to acquire the lock, one of them will eventually acquire it and proceed.
### Advantages of Locks
- **Control Over Access**: Locks provide the programmer control over thread access to shared resources, ensuring only one thread can be in the critical section at any time.
- **Coordination in Concurrency**: Locks help manage the OS’s otherwise unpredictable scheduling, allowing for structured and safe access to shared data.
## 28.2 Pthread Locks
- **Mutex** stands for **Mutual Exclusion**. It is a type of lock used to ensure that only one thread can access a critical section at a time.
- When one thread acquires the mutex and enters a critical section, all other threads are excluded from entering that section until the mutex is released.
### POSIX Mutex Syntax
- In the POSIX library (used in many Unix-based systems), a mutex is created using `pthread_mutex_t` and is initialized with `PTHREAD_MUTEX_INITIALIZER`.
```c++
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER; // declare and initialize mutex

pthread_mutex_lock(&lock);   // acquire the lock
balance = balance + 1;       // critical section
pthread_mutex_unlock(&lock); // release the lock
```
- **Wrapper Functions**: In this example, `Pthread_mutex_lock` and `Pthread_mutex_unlock` are wrappers that handle any errors upon locking or unlocking, ensuring the program exits on failure.
### Passing Mutex Variables
- The POSIX functions `pthread_mutex_lock()` and `pthread_mutex_unlock()` take the **mutex variable as an argument**.
- This flexibility allows developers to use different mutexes for different data structures or variables, enabling more precise control over concurrency.
#### Coarse-Grained Locking
- Uses a **single lock** to protect multiple critical sections or variables.
- **Pros**: Simple to implement and minimizes the number of locks required.
- **Cons**: Reduces concurrency since only one thread can enter any critical section at a time, even if they do not interfere with each other.
#### Fine-Grained Locking
- Uses **different locks** for different critical sections or data structures.
- **Pros**: Increases concurrency by allowing multiple threads to hold different locks and access different protected resources simultaneously.
- **Cons**: More complex to implement and may require more careful management of lock dependencies to avoid deadlocks.

## 28.3 Building A Lock
- The objective of designing a lock is to achieve **mutual exclusion** efficiently, minimizing overhead while allowing safe access to critical sections.
- Efficient locks ensure that only one thread can access the critical section at a time, with low performance cost.
### Key Requirements for Building Locks
- **Hardware Support**: Building reliable locks requires atomic operations that ensure no interruption during a critical section.
- **OS Support**: The OS plays a role in managing locks by providing mechanisms to handle contention (multiple threads wanting the lock) and ensuring fair scheduling of threads.
- Hardware primitives, such as **atomic instructions** (e.g., test-and-set, compare-and-swap), are essential for creating locks.
- These instructions allow threads to test and update a lock's state in one indivisible step, ensuring that no two threads can enter a critical section simultaneously.
### OS Role in Locking
- The OS supports efficient locking by providing system calls that manage thread state (e.g., putting a thread to sleep if it fails to acquire the lock).
- This helps prevent **busy-waiting**, where threads repeatedly check the lock's status, wasting CPU cycles.
### Challenges in Lock Design
- **Performance**: Locks must be lightweight to minimize impact on system performance.
- **Fairness**: Locks should prevent starvation, ensuring all threads eventually gain access to the critical section.
- **Scalability**: The lock implementation should handle a large number of threads without significant contention.

## 28.4 Evaluating Locks
- Before building a lock, it’s essential to establish criteria to evaluate its effectiveness. We focus on three primary goals: **mutual exclusion**, **fairness**, and **performance**.
### Mutual Exclusion
- The primary purpose of a lock is to ensure **mutual exclusion**. This means only one thread can enter the critical section at a time, preventing conflicts and ensuring data integrity.
- The lock should reliably block other threads from accessing shared data while a thread holds the lock.
### Fairness
- Fairness ensures that each thread has a fair opportunity to acquire the lock when it becomes free.
- **Starvation** is an extreme fairness issue where a thread waits indefinitely for the lock, unable to proceed. An effective lock implementation avoids starvation, ensuring that all threads eventually get access.
### Performance
- **Performance** measures the overhead added by using a lock. There are three main scenarios to consider:
    1. **No Contention**: When only one thread is accessing the lock, how efficient is it to acquire and release the lock?
    2. **Single CPU, Multiple Threads**: When multiple threads on a single CPU contend for the lock, does the implementation handle contention efficiently?
    3. **Multiple CPUs, Multiple Threads**: In multi-core systems, threads on different CPUs may contend for the same lock. How does the lock perform in this high-contention environment?

## 28.5 Controlling Interrupts
### Concept of Disabling Interrupts for Mutual Exclusion
- In early single-processor systems, disabling interrupts was a method used to ensure **mutual exclusion** in critical sections.
- **How it works**:
    - **DisableInterrupts()**: Before entering a critical section, the program disables interrupts, ensuring that no other code can interrupt the execution.
    - **EnableInterrupts()**: After the critical section, interrupts are re-enabled to allow normal execution.
- This method ensures that code within the critical section runs **atomically** since it cannot be interrupted.
#### Advantages
- **Simplicity**: The method is straightforward and easy to understand.
- **Atomic Execution**: Disabling interrupts guarantees that a thread within a critical section cannot be interrupted, ensuring atomicity.
#### Disadvantages
- **Trust Issues**:
    - Any thread can disable interrupts, which requires **trust** that it won’t misuse this capability.
    - A thread could disable interrupts and **monopolize the processor**, potentially freezing the system if it goes into an infinite loop.
- **Limited to Single Processors**:
    - This approach fails in **multiprocessor** systems. While one CPU’s interrupts are disabled, other CPUs can still execute code that might interfere with the critical section.
- **System Stability**:
    - Disabling interrupts for extended periods can lead to **lost interrupts**. For example, if an interrupt from a device (like a disk) is missed, the OS may fail to respond, causing potential system issues.
### Limited Use in Modern Systems
- Due to its limitations, interrupt disabling is rarely used as a general-purpose synchronization mechanism.
- **Typical Use**: The OS may still use this method for short, critical operations within its own code, where it has control and trust is not an issue.

## 28.6 A Failed Attempt: Just Using Loads/Stores
### Introduction to Lock Using a Flag Variable
- The first attempt to create a lock uses a single **flag variable** to indicate if a lock is held by any thread.
- **Lock Mechanism**:
    - When a thread calls `lock()`, it checks if the flag is set to `0` (indicating the lock is free).
    - If free, it sets the flag to `1` (locking it) and enters the critical section.
    - After completing the critical section, the thread calls `unlock()`, setting the flag back to `0` to release the lock.
```c++
typedef struct __lock_t { int flag; } lock_t;

void init(lock_t *mutex) {
    mutex->flag = 0;  // 0 indicates lock is available, 1 means it's held
}

void lock(lock_t *mutex) {
    while (mutex->flag == 1); // spin-wait if lock is held
    mutex->flag = 1;          // acquire the lock
}

void unlock(lock_t *mutex) {
    mutex->flag = 0;          // release the lock
}
```
### Correctness Issue (Race Condition)
- **Race Condition**: This approach does not ensure **mutual exclusion** due to potential interleaving of instructions.
- **Example of Race Condition**:
    - If two threads call `lock()` simultaneously, they could both pass the `while` check when `flag=0` before either sets it to `1`.
    - Both threads then proceed into the critical section, violating mutual exclusion.
- **Result**: Both threads may execute the critical section at the same time, which is incorrect and can lead to inconsistent or unexpected results.
### Performance Issue (Spin-Waiting)
- **Spin-Waiting**: When one thread is in the critical section, other threads that call `lock()` simply keep checking the flag in a loop.
- **Inefficiency**:
    - On a single CPU system, the waiting thread will repeatedly check the flag even though the current holder cannot release it until a **context switch** occurs.
    - This wastes CPU cycles as the waiting thread does nothing useful.

## 28.7 Building Working Spin Locks with Test-And-Set
- As disabling interrupts and simple load/store operations failed for multiprocessor systems, **hardware support** became essential for achieving mutual exclusion.
- The **test-and-set instruction** is one of the earliest and simplest forms of hardware support for building locks, first seen in early multiprocessor systems (e.g., Burroughs B5000).
### Test-and-Set Instruction
- **Definition**: `TestAndSet()` atomically reads the old value of a memory location and sets it to a new value.
```c++
int TestAndSet(int *old_ptr, int new) {
    int old = *old_ptr; // fetch old value
    *old_ptr = new;     // set new value
    return old;         // return old value
}
```
* **Key Feature**: The operation is atomic, meaning the test (check old value) and set (update to new value) are performed as a single, indivisible operation.
### Using Test-and-Set for Spin Locks
- **Structure of the Lock**:
```c++
typedef struct __lock_t { 
    int flag; 
} lock_t;

void init(lock_t *lock) {
    lock->flag = 0; // 0: lock available, 1: lock held
}

void lock(lock_t *lock) {
    while (TestAndSet(&lock->flag, 1) == 1)
        ; // spin-wait
}

void unlock(lock_t *lock) {
    lock->flag = 0;
}
```
- **Working Mechanism**:
    - **Acquiring the Lock**:
        - A thread calls `lock()`, which uses `TestAndSet()` on `flag`.
        - If `flag` is `0` (lock available), `TestAndSet()` returns `0` and sets `flag` to `1`, allowing the thread to enter the critical section.
    - **Contending for the Lock**:
        - If another thread tries to call `lock()` while `flag` is `1` (lock held), `TestAndSet()` returns `1`, causing the thread to spin-wait until the lock is available.
    - **Releasing the Lock**:
        - The thread holding the lock calls `unlock()`, which resets `flag` to `0`, allowing waiting threads to acquire the lock.
### Advantages and Limitations of Spin Locks
- **Advantages**:
    - Simple to implement using atomic operations.
    - Effective on multiprocessor systems where threads may run concurrently.
- **Limitations**:
    - **Spin-waiting** wastes CPU cycles, as waiting threads continuously check the lock.
    - On single-processor systems, a spin lock requires **preemptive scheduling**; without it, a spinning thread will never release the CPU, leading to inefficiency.
## 28.8 Evaluating Spin Locks
- **Correctness**:
    - Spin locks provide **mutual exclusion** by ensuring that only one thread can hold the lock and enter the critical section at a time.
    - In terms of correctness, the spin lock meets its primary goal.
- **Fairness**:
    - Spin locks do not guarantee fairness. A waiting thread may **starve**, especially under heavy contention, because there is no mechanism to ensure that waiting threads will acquire the lock in order.
    - This lack of fairness can lead to a situation where some threads never access the critical section, especially if a thread repeatedly reacquires the lock before others.
- **Performance**:
    - The effectiveness of spin locks depends on the hardware setup:
        - **Single Processor**: Performance overhead is high. If the thread holding the lock is preempted, every other waiting thread will waste an entire time slice spinning before yielding the CPU. This results in significant CPU cycle wastage.
        - **Multiple Processors**: Spin locks work better, as waiting threads can spin on separate CPUs without blocking the processor holding the lock. When the lock-holding thread completes its critical section, a waiting thread on another CPU can quickly acquire it. This setup is effective if the number of threads roughly matches the number of CPUs, minimizing cycle waste.
### Improving Spin Locks with Atomic Instructions
- While **test-and-set** provides basic atomic locking, alternative instructions like **Compare-and-Swap (CAS)** offer more advanced functionality.
- **Compare-and-Swap (CAS) Operation**:
    - The **CAS** instruction checks a memory location to see if it contains an expected value. If it does, CAS updates the location with a new value. If not, the memory location remains unchanged.
```c++
int CompareAndSwap(int *ptr, int expected, int new) {
    int original = *ptr;         // Read the original value
    if (original == expected)    // Compare with the expected value
        *ptr = new;              // Set to new value if match
    return original;             // Return the original value
}
```
* **CAS Advantages**:
	- CAS allows more complex atomic operations, offering flexibility for implementing various locking and synchronization mechanisms.
	- With CAS, threads can avoid unnecessary spinning, as the check and update are atomic, reducing contention on the shared lock variable.
## 28.9 Compare-And-Swap
- The **compare-and-swap (CAS)** instruction, also known as **compare-and-exchange** on some systems, is a hardware primitive used for synchronization.
- CAS compares a value at a memory location (`ptr`) with an `expected` value:
    - If the value at `ptr` matches `expected`, it updates `ptr` to a new value (`new`).
    - If it does not match, CAS does nothing.
- CAS always returns the original value at the memory location, allowing the caller to know whether the swap was successful.
- ### Building a Lock Using CAS
```c++
void lock(lock_t *lock) {
    while (CompareAndSwap(&lock->flag, 0, 1) == 1)
        ; // spin
}
```
- **How It Works**:
    - The lock attempts to set `lock->flag` to `1` (locked) if the current value is `0` (unlocked).
    - If `flag` is already `1`, the thread spins (waits) until `flag` becomes `0`, indicating the lock is free.
    - CAS provides **atomicity** for the `compare` and `swap` steps, ensuring only one thread can acquire the lock at a time.
### Power of CAS in Synchronization
- **CAS vs. Test-and-Set**:
    - CAS is generally more **flexible and powerful** than test-and-set because it allows more complex synchronization mechanisms.
    - CAS can be used in various lock-free synchronization techniques, providing the foundation for future developments in concurrent programming.

## 28.10 Load-Linked and Store-Conditional
- **Load-Linked (LL)** and **Store-Conditional (SC)** are special instructions found on platforms like MIPS, ARM, Alpha, and PowerPC, designed for atomic operations in concurrent programming.
- **Load-Linked (LL)**: This works like a typical load operation, fetching the value from memory into a register.
- **Store-Conditional (SC)**: Attempts to store a new value to the memory address only if no other stores have occurred at that address since the last LL.
    - If successful, it updates the value and returns `1`.
    - If unsuccessful (due to an intervening store by another thread), it does not update and returns `0`.
### Using LL/SC to Build a Lock
- A lock can be implemented by having a thread **spin** on `LoadLinked()` until it reads `0` (indicating the lock is free).
- The thread then calls `StoreConditional()` to try setting the lock to `1`.
    - If successful, it means the lock is acquired, and the thread can enter the critical section.
    - If unsuccessful (another thread acquired it in the meantime), the thread loops back to try again.
```c++
void lock(lock_t *lock) {
    while (1) {
        while (LoadLinked(&lock->flag) == 1)
            ; // spin until flag is 0 (lock is free)
        if (StoreConditional(&lock->flag, 1) == 1)
            return; // success, lock acquired
        // otherwise, try again
    }
}
```
### Failure Case and Mutual Exclusion
- **Failure of SC**: Occurs when two threads execute `LoadLinked()` and both get `0`. If both then try `StoreConditional()`:
    - Only one will succeed, as SC only allows the first thread to update the value.
    - This ensures **mutual exclusion**: only one thread holds the lock at any time.
### Shorter Lock Implementation
- An alternative, more concise form of the `lock()` function combines the conditions, this code is equivalent to the original but shorter, as it leverages short-circuit evaluation:
```c++
void lock(lock_t *lock) {
    while (LoadLinked(&lock->flag) || !StoreConditional(&lock->flag, 1))
        ; // spin
}
```

## 28.11 Fetch-And-Add
- **Purpose**: The fetch-and-add instruction atomically increments a memory value and returns its original value.
```c++
int FetchAndAdd(int *ptr) {
    int old = *ptr;
    *ptr = old + 1;
    return old;
}
```
- **Atomic Operation**: Ensures that the increment operation is atomic, meaning no other thread can modify the value until this operation completes.
### Ticket Lock Using Fetch-And-Add
- **Ticket Lock Structure**: Instead of a single lock variable, the ticket lock uses two variables:
    - `ticket`: Tracks the order in which threads request the lock.
    - `turn`: Keeps track of the current thread's turn.
- **How It Works**:
    - When a thread wants to acquire the lock, it performs a `FetchAndAdd` on `ticket` to get its own “ticket number” (let's call it `myturn`).
    - The thread then waits until `myturn == turn`, indicating it’s now that thread’s turn to enter the critical section.
- **Unlocking**:
    - When the thread completes the critical section, it increments `turn`, allowing the next thread (if any) to enter.
### Benefits of Ticket Locks
- **Fairness**: Ticket locks ensure **fairness** by providing a guaranteed ordering. Every thread receives a ticket and will eventually get a turn, avoiding starvation.
- **Progress Guarantee**: Every thread will eventually acquire the lock, as threads progress through the critical section in the order of their ticket numbers.
```c++
typedef struct __lock_t {
    int ticket;
    int turn;
} lock_t;

void init(lock_t *lock) {
    lock->ticket = 0;
    lock->turn = 0;
}

void lock(lock_t *lock) {
    int myturn = FetchAndAdd(&lock->ticket);
    while (lock->turn != myturn)
        ; // spin-wait
}

void unlock(lock_t *lock) {
    lock->turn = lock->turn + 1;
}
```
### Comparison with Previous Locks
- **Spin Locks and Fairness**: Unlike spin locks (which lack fairness guarantees), ticket locks provide a clear queue, ensuring each thread has a predictable chance to acquire the lock.
- **Avoiding Starvation**: With ticket locks, once a thread has a ticket, it will eventually proceed to the critical section, preventing any possibility of starvation seen in basic spin locks.

## 28.12 Too Much Spinning: What Now?
### Problem with Simple Hardware-Based Locks
- **Inefficiency in Single Processor Systems**: In a single-processor system, if one thread holds the lock and is interrupted, other threads trying to acquire the lock will simply spin, wasting CPU cycles.
- **Wasted Time Slices**: Threads that spin while the lock-holding thread is inactive consume entire time slices without doing useful work. This waste is compounded with multiple threads, as multiple threads may spin simultaneously, each wasting its time slice. 
### Drawbacks of Spinning in Ticket Locks
- **Wasted CPU Cycles**: In situations where a thread holding the lock is not running (e.g., it was preempted), other threads waste resources by continuously checking the lock status without making progress.
- **Increased Waste with Multiple Threads**: In an `N`-thread system, `N-1` threads may be spinning and wasting CPU cycles, especially problematic on a single-core system.
### Solution: OS Support for Blocking Locks
- **Avoiding Spinning with Blocking**:
    - To avoid spinning, we introduce a mechanism where threads waiting for a lock can be put to sleep by the OS instead of constantly spinning.
    - When the lock becomes available, the OS wakes one of the sleeping threads to acquire the lock, saving CPU cycles that would otherwise be wasted.
- **OS and Hardware Collaboration**:
    - While hardware primitives like `test-and-set` or `compare-and-swap` are essential for atomic operations, reducing spinning in lock mechanisms also requires support from the OS to manage thread states effectively.

By combining hardware atomic instructions and OS-managed blocking, we can create locks that are more efficient in CPU usage, especially in multi-threaded and multi-core systems. This approach reduces unnecessary spinning and optimizes the use of CPU resources.

## 28.14 Using Queues: Sleeping Instead Of Spinning
### Problem with Scheduler-Based Approaches
- Previous approaches left too much to the scheduler’s discretion, leading to inefficiencies and potential starvation in lock acquisition.
- Simple spin locks or yield-based locks depend on the scheduler to eventually allow each waiting thread a chance at the lock, which can result in unnecessary spinning or yielding.
### Using a Queue for Order Control
- To manage which thread gets the lock next, we introduce a queue that tracks threads waiting to acquire the lock.
- With a queue, the lock can be passed in order, ensuring fairness and avoiding starvation.
### New OS Support: `park()` and `unpark()`
- **`park()`**: Puts a calling thread to sleep if it tries to acquire an already held lock.
- **`unpark(threadID)`**: Wakes up a specified thread, allowing it to attempt acquiring the lock when the lock becomes free.
### Queue-Based Lock Structure
- The lock structure uses:
    - **flag**: Indicates whether the lock is held.
    - **guard**: Acts as a spin lock around `flag` and queue operations.
    - **queue**: Stores thread IDs of waiting threads.
```c++
void lock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1) ; // acquire guard lock
    if (m->flag == 0) {
        m->flag = 1; // acquire lock
        m->guard = 0;
    } else {
        queue_add(m->q, gettid());
        setpark(); // indicate about to park
        m->guard = 0;
        park(); // put to sleep if lock is held
    }
}

void unlock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1) ; // acquire guard lock
    if (queue_empty(m->q))
        m->flag = 0; // release lock if no waiting threads
    else
        unpark(queue_remove(m->q)); // wake next waiting thread
    m->guard = 0;
}
```
### Role of `guard` as a Spin Lock
- **Guard** prevents race conditions by locking flag and queue manipulations, ensuring that only one thread can modify them at a time.
- Although `guard` involves some spinning, it is minimal, as it only surrounds lock/unlock operations, not user-defined critical sections.
### Preventing the Wakeup/Waiting Race
- The **wakeup/waiting race** occurs when a thread is about to park but gets interrupted, allowing another thread to release the lock, resulting in the first thread potentially sleeping indefinitely.
- **Solution**: Introduce the `setpark()` system call to signal intent to park, which ensures that if another thread calls `unpark` on it before it parks, the `park()` call will return immediately instead of sleeping.
### Benefits of Queue-Based Lock
- **Fairness**: Ensures each thread waiting for the lock eventually gets it in order.
- **Reduced Spinning**: Threads go to sleep instead of spinning, reducing CPU waste.
- **Avoids Starvation**: The queue provides a controlled, fair access sequence, reducing the risk of any thread waiting indefinitely.
