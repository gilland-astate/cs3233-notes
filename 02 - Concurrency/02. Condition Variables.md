# Lock-based Concurrent Data Structures
## 29.1 Concurrent Counters
### Simple Non-Thread-Safe Counter
- **Structure**:
    - A basic `counter_t` struct contains a single integer `value`.
    - Functions include `init()`, `increment()`, `decrement()`, and `get()` (Figure 29.1).
- **Limitation**:
    - Not thread-safe; concurrent updates lead to race conditions.
```c++
typedef struct __counter_t {
    int value;
} counter_t;

void init(counter_t *c) {
    c->value = 0;
}

void increment(counter_t *c) {
    c->value++;
}

void decrement(counter_t *c) {
    c->value--;
}

int get(counter_t *c) {
    return c->value;
}

```
### Making Counters Thread-Safe
- **Solution**:
    - Add a lock to the `counter_t` structure (Figure 29.2).
    - Use `pthread_mutex_lock` and `pthread_mutex_unlock` around critical sections (increment, decrement, and get operations).
- **Drawbacks**:
    - Correct but not scalable.
    - High contention when multiple threads frequently access the counter, leading to poor performance.
```c++
typedef struct __counter_t {
    int value;
    pthread_mutex_t lock;
} counter_t;

void init(counter_t *c) {
    c->value = 0;
    pthread_mutex_init(&c->lock, NULL);
}

void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}

void decrement(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value--;
    pthread_mutex_unlock(&c->lock);
}

int get(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    int rc = c->value;
    pthread_mutex_unlock(&c->lock);
    return rc;
}
```
- **Experiment Results**:
    - With increasing threads, the time to complete updates increases significantly.
    - Example: On a 4-core machine, performance degrades due to contention for the single lock.
### Scalable Counters
- **Objective**: Improve performance by reducing contention while maintaining correctness.
- **Technique**: **Approximate Counters**:
    - Break the counter into:
        1. **Local Counters**: One per CPU core, updated independently by threads running on that core.
        2. **Global Counter**: Updated periodically by aggregating local counters.
    - Use separate locks for each local counter and the global counter.
### Approximate Counter Implementation
- **Structure** (Figure 29.4):
    - `global`: Holds the approximate total count.
    - `local[NUMCPUS]`: Per-CPU counters for local updates.
    - `glock` and `llock[NUMCPUS]`: Mutexes for the global and local counters.
    - `threshold`: Determines how often local counters update the global counter.
- **Operations**:
    - **Update**:
        - Increment the local counter (protected by its lock).
        - If the local counter exceeds the threshold, add its value to the global counter (protected by the global lock).
    - **Get**:
        - Return the value of the global counter (approximate).
- **Advantages**:
    - Minimizes contention as most updates occur locally.
    - Scales well with the number of CPUs.
```c++
typedef struct __counter_t {
    int global;                // global count
    pthread_mutex_t glock;     // global lock
    int local[NUMCPUS];        // per-CPU counts
    pthread_mutex_t llock[NUMCPUS]; // per-CPU locks
    int threshold;             // update threshold
} counter_t;

void init(counter_t *c, int threshold) {
    c->threshold = threshold;
    c->global = 0;
    pthread_mutex_init(&c->glock, NULL);
    for (int i = 0; i < NUMCPUS; i++) {
        c->local[i] = 0;
        pthread_mutex_init(&c->llock[i], NULL);
    }
}

void update(counter_t *c, int threadID, int amt) {
    int cpu = threadID % NUMCPUS;  // determine which local counter to use
    pthread_mutex_lock(&c->llock[cpu]);
    c->local[cpu] += amt;
    if (c->local[cpu] >= c->threshold) {
        pthread_mutex_lock(&c->glock);
        c->global += c->local[cpu];
        pthread_mutex_unlock(&c->glock);
        c->local[cpu] = 0;
    }
    pthread_mutex_unlock(&c->llock[cpu]);
}

int get(counter_t *c) {
    pthread_mutex_lock(&c->glock);
    int val = c->global;
    pthread_mutex_unlock(&c->glock);
    return val;  // approximate value
}
```
#### Performance and Trade-Offs
- **Threshold (S)**:
    - Determines the frequency of local-to-global updates.
    - Low `S`: More accurate global count but higher contention and lower performance.
    - High `S`: Better performance due to less contention but less accurate global count.
- **Results**:
    - High thresholds yield near-perfect scaling in multi-threaded workloads.
    - The global count’s inaccuracy is bounded by `S × NUMCPUS`.

## 29.2 Concurrent Linked Lists
- **Structure**:
    - **Node**: Contains a `key` and a pointer to the `next` node.
    - **List**: Contains a pointer to the head node and a lock for synchronization.
```c++
// Node structure
typedef struct __node_t {
    int key;
    struct __node_t *next;
} node_t;

// List structure
typedef struct __list_t {
    node_t *head;
    pthread_mutex_t lock;
} list_t;

// Initialize the list
void List_Init(list_t *L) {
    L->head = NULL;
    pthread_mutex_init(&L->lock, NULL);
}

// Insert a key into the list
int List_Insert(list_t *L, int key) {
    pthread_mutex_lock(&L->lock);
    node_t *new = malloc(sizeof(node_t));
    if (new == NULL) {
        perror("malloc");
        pthread_mutex_unlock(&L->lock);
        return -1; // fail
    }
    new->key = key;
    new->next = L->head;
    L->head = new;
    pthread_mutex_unlock(&L->lock);
    return 0; // success
}

// Look up a key in the list
int List_Lookup(list_t *L, int key) {
    pthread_mutex_lock(&L->lock);
    node_t *curr = L->head;
    while (curr) {
        if (curr->key == key) {
            pthread_mutex_unlock(&L->lock);
            return 0; // success
        }
        curr = curr->next;
    }
    pthread_mutex_unlock(&L->lock);
    return -1; // failure
}
```
#### Issues with the Basic Implementation
- **Lock Usage**: Locks are held for the entire duration of `List_Insert()` and `List_Lookup()`, even during non-critical operations like `malloc()`.
- **Error-Prone**: Exceptional control flows (e.g., `malloc()` failure) require releasing the lock explicitly, increasing the risk of bugs (e.g., forgetting to unlock).
### Improved Concurrent Linked List
- **Solution**:
    - Rearrange code to hold locks only during critical sections.
    - Simplify `List_Lookup()` to ensure a single exit path.
```c++
// Initialize the list
void List_Init(list_t *L) {
    L->head = NULL;
    pthread_mutex_init(&L->lock, NULL);
}

// Insert a key into the list
int List_Insert(list_t *L, int key) {
    // Non-critical section
    node_t *new = malloc(sizeof(node_t));
    if (new == NULL) {
        perror("malloc");
        return -1; // fail
    }
    new->key = key;

    // Critical section
    pthread_mutex_lock(&L->lock);
    new->next = L->head;
    L->head = new;
    pthread_mutex_unlock(&L->lock);

    return 0; // success
}

// Look up a key in the list
int List_Lookup(list_t *L, int key) {
    int rv = -1; // default to failure
    pthread_mutex_lock(&L->lock);
    node_t *curr = L->head;
    while (curr) {
        if (curr->key == key) {
            rv = 0; // success
            break;
        }
        curr = curr->next;
    }
    pthread_mutex_unlock(&L->lock);
    return rv;
}
```
#### Scalability Issues
- **Single Lock Bottleneck**:
    - The single lock limits concurrency as only one thread can access the list at a time.
    - For large lists or high contention, performance degrades significantly.
### Advanced Technique: Hand-Over-Hand Locking
- **Concept**:
    - Use a lock per node instead of a single lock for the entire list.
    - Acquire the next node’s lock before releasing the current node’s lock during traversal (hence "hand-over-hand").
- **Advantages**: Enables multiple threads to traverse or update the list concurrently.
- **Drawbacks**:
    - Significant overhead from acquiring and releasing locks for each node.
    - Rarely faster than using a single lock, even for large lists.
**Key Insight**: In most practical scenarios, a single lock is simpler and performs adequately. Hand-over-hand locking might be beneficial in highly concurrent environments but is often impractical.
### Possible Improvements
- **Hybrid Locking**:
    - Acquire a single lock for multiple nodes (e.g., every N nodes).
    - Balances reduced locking overhead with increased concurrency.
- **Fine-Grained Locking**:
    - Combine node-level locks with bulk operations to optimize performance under specific workloads.

## 29.3 Concurrent Queues
- A queue data structure where multiple threads can safely perform enqueue (insert) and dequeue (remove) operations concurrently.
- Instead of a "big lock" solution, Michael and Scott’s approach uses two separate locks for improved concurrency.
### Data Structure
- **Node Structure**:
    - Represents each element in the queue.
    - Contains:
        - `value`: The data stored in the node.
        - `next`: A pointer to the next node.
- **Queue Structure**:
    - Contains:
        - `head`: Points to the front of the queue (first node to dequeue).
        - `tail`: Points to the rear of the queue (last node to enqueue).
        - `head_lock` and `tail_lock`: Separate locks for managing head and tail operations, enabling concurrent enqueue and dequeue.
```c++
typedef struct __node_t {
    int value;
    struct __node_t *next;
} node_t;

typedef struct __queue_t {
    node_t *head;
    node_t *tail;
    pthread_mutex_t head_lock, tail_lock;
} queue_t;
```
- **Dummy Node**:
	- A dummy node is allocated at initialization.
	- Both `head` and `tail` point to the dummy node initially.
	- This dummy node simplifies head and tail operations by avoiding special cases for an empty queue.
```c++
void Queue_Init(queue_t *q) {
    node_t *tmp = malloc(sizeof(node_t));
    tmp->next = NULL;
    q->head = q->tail = tmp;
    pthread_mutex_init(&q->head_lock, NULL);
    pthread_mutex_init(&q->tail_lock, NULL);
}
```
### Enqueue Operation
- **Steps**:
    1. Allocate a new node for the value to be added.
    2. Lock the `tail_lock` to ensure exclusive access to the tail.
    3. Add the new node to the tail and update the `tail` pointer.
    4. Unlock the `tail_lock`.
- **Concurrency**: Only the `tail_lock` is used, allowing concurrent dequeue operations to proceed.
```c++
void Queue_Enqueue(queue_t *q, int value) {
    node_t *tmp = malloc(sizeof(node_t));
    assert(tmp != NULL);
    tmp->value = value;
    tmp->next = NULL;

    pthread_mutex_lock(&q->tail_lock);
    q->tail->next = tmp;
    q->tail = tmp;
    pthread_mutex_unlock(&q->tail_lock);
}
```
### Dequeue Operation
- **Steps**:
    1. Lock the `head_lock` to ensure exclusive access to the head.
    2. Check if the queue is empty by inspecting the `head->next` pointer.
    3. If not empty:
        - Retrieve the value of the new head.
        - Update the `head` pointer to the new head.
        - Free the old head.
    4. Unlock the `head_lock`.
- **Concurrency**: Only the `head_lock` is used, allowing concurrent enqueue operations to proceed.
```c++
int Queue_Dequeue(queue_t *q, int *value) {
    pthread_mutex_lock(&q->head_lock);
    node_t *tmp = q->head;
    node_t *new_head = tmp->next;
    if (new_head == NULL) { // Queue is empty
        pthread_mutex_unlock(&q->head_lock);
        return -1;
    }
    *value = new_head->value;
    q->head = new_head;
    pthread_mutex_unlock(&q->head_lock);
    free(tmp);
    return 0; // Success
}
```
### Key Features
1. **Two-Lock Design**:
    - Separate locks for `head` and `tail` enable greater concurrency.
    - Dequeue operations only block other dequeues, and enqueue operations only block other enqueues.
2. **Dummy Node**:
    - Simplifies queue operations by avoiding special cases for empty or single-node queues.
### Limitations
- **Queue Still Blocking**:
    - While enqueue and dequeue operations are more concurrent, they still block if a thread holds the corresponding lock.
- **Not Bounded**:
    - This implementation does not account for full queues. A bounded queue implementation (discussed later) would include mechanisms to handle such cases.

# Condition Variables
- **Scenario**: A parent thread needs to wait for a child thread to complete before continuing execution.
- **Desired Output**:
```
parent: begin
child
parent: end
```
- **Challenges**:
    - Inefficient waiting can waste CPU cycles.
    - A proper mechanism is needed to allow the parent thread to wait without excessive CPU usage.
### Inefficient Solution: Spin-Waiting
- **Spin-Waiting Example**:
```c++
volatile int done = 0;

void *child(void *arg) {
    printf("child\n");
    done = 1;
    return NULL;
}

int main() {
    printf("parent: begin\n");
    pthread_t c;
    Pthread_create(&c, NULL, child, NULL);
    while (done == 0)
        ; // spin
    printf("parent: end\n");
    return 0;
}
```
- **How It Works**:
    - The parent thread continuously checks (`spins`) on the `done` variable until the child thread sets it to `1`.
- **Problems with Spin-Waiting**:
    - **Wastes CPU Cycles**: The parent thread continuously polls, consuming CPU time without doing useful work.
    - **Scalability Issues**: In multi-threaded systems, excessive spinning can degrade performance.
    - **Incorrectness**: Spin-based approaches can fail under certain conditions (e.g., reordering due to compiler optimizations).
### Efficient Solution: Using Synchronization Primitives
- **Goal**: Provide a mechanism for a thread to wait for a condition to become true without wasting CPU cycles.
- **Requirements**:
    - Ability to put a thread to sleep until the condition is met.
    - A way to notify the waiting thread when the condition is satisfied.
### The Crux
- **Key Question**: How can we efficiently and correctly implement a mechanism where a thread waits for a condition to become true?
- **Approach**:
    - Avoid spin-waiting by using synchronization primitives such as **condition variables**.
    - Condition variables allow a thread to sleep until a condition is explicitly signaled by another thread, ensuring efficient CPU usage and correctness.
-----
## 30.1 Definition and Routines
- A **condition variable** allows threads to wait for a specific condition to become true before proceeding.
- Threads use **wait()** to sleep until the condition is satisfied and **signal()** to wake sleeping threads when the condition changes.
```c++
pthread_cond_t c;
pthread_cond_wait(pthread_cond_t *c, pthread_mutex_t *m);
pthread_cond_signal(pthread_cond_t *c);
```
- **wait()**: Atomically releases the lock and puts the thread to sleep. When the thread wakes, it reacquires the lock.
- **signal()**: Wakes one sleeping thread (if any) waiting on the condition.
- A mutex must be locked when calling **wait()** or **signal()** to prevent race conditions.
### Example: Parent Waiting for Child
```
parent: begin
child
parent: end
```
```c++
int done = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t c = PTHREAD_COND_INITIALIZER;

void thr_exit() {
    Pthread_mutex_lock(&m);
    done = 1;
    Pthread_cond_signal(&c);
    Pthread_mutex_unlock(&m);
}

void *child(void *arg) {
    printf("child\n");
    thr_exit();
    return NULL;
}

void thr_join() {
    Pthread_mutex_lock(&m);
    while (done == 0)  // Use a while loop to avoid race conditions
        Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}

int main() {
    printf("parent: begin\n");
    pthread_t p;
    Pthread_create(&p, NULL, child, NULL);
    thr_join();
    printf("parent: end\n");
    return 0;
}
```
- **State Variable**:
    - Tracks the condition (`done = 1` when the child is finished).
    - Without it, a thread might sleep forever if a signal is sent before a thread is waiting.
- **Mutex**:
    - Ensures atomicity when modifying or checking the condition variable.
    - Prevents race conditions where a signal is missed due to improper synchronization.
### Common Mistakes and Issues
- **No State Variable**: If a thread signals when no one is waiting, the signal is lost.
```c++
void thr_exit() {
    Pthread_cond_signal(&c);
}

void thr_join() {
    Pthread_cond_wait(&c, &m);
}
```
- **No Mutex**: Leads to race conditions. A thread might miss the condition change and sleep forever.
```c++
void thr_exit() {
    done = 1;
    Pthread_cond_signal(&c);
}

void thr_join() {
    if (done == 0)
        Pthread_cond_wait(&c, &m);
}
```
### Best Practices
- Always use a **state variable** to track the condition of interest.
- Always protect condition variables with a **mutex** to ensure atomicity.
- Use a **while loop** instead of an `if` to recheck conditions after waking up.

## 30.2 The Producer/Consumer (Bounded Buffer) Problem
- The producer/consumer (or bounded buffer) problem is a classic synchronization problem where:
    - **Producers** generate data and place it in a shared buffer.
    - **Consumers** retrieve data from the buffer and process it.
- The buffer has limited capacity, requiring synchronization to avoid:
    - Producers writing into a full buffer.
    - Consumers reading from an empty buffer.
### Problem Setup
- **Shared Buffer**: A single-slot buffer (later generalized to multiple slots).
- **Basic Routines**:
```c++
void put(int value) {
    assert(count == 0);
    count = 1;
    buffer = value;
}

int get() {
    assert(count == 1);
    count = 0;
    return buffer;
}
```
- **Producer Thread**: Inserts items into the buffer.
- **Consumer Thread**: Retrieves items from the buffer.
### Challenges
- **Race Conditions**: Multiple producers or consumers can interfere with each other, leading to incorrect results.
- **Synchronization**: Proper coordination is required to ensure producers wait when the buffer is full, and consumers wait when it is empty.
### Broken Solutions
1. **Single Lock Without Condition Variables**:
    - A single lock cannot distinguish between the states of the buffer (full/empty).
    - Both producers and consumers can proceed incorrectly, causing assertion failures.
2. **Single Condition Variable with `if` Statements**:
    - Using a single condition variable works with one producer and one consumer.
    - Fails with multiple consumers or producers due to:
        - **Missed Signals**: A consumer may consume and signal another consumer, leaving producers waiting indefinitely.
        - **State Changes**: Condition state can change between a signal and the thread running.
    - **Solution**: Replace `if` with `while` to ensure conditions are re-checked upon waking.
### Correct Single Buffer Solution
- **Two Condition Variables**:
    - **`fill`**: Used by consumers to wait until the buffer has data.
    - **`empty`**: Used by producers to wait until the buffer has space.
```c++
cond_t empty, fill;
mutex_t mutex;

void *producer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == 1)
            Pthread_cond_wait(&empty, &mutex);
        put(i);
        Pthread_cond_signal(&fill);
        Pthread_mutex_unlock(&mutex);
    }
}

void *consumer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == 0)
            Pthread_cond_wait(&fill, &mutex);
        int tmp = get();
        Pthread_cond_signal(&empty);
        Pthread_mutex_unlock(&mutex);
        printf("%d\n", tmp);
    }
}
```
### Extending to a Multi-slot Buffer
- **Motivation**: Increase concurrency and reduce context switching by allowing multiple items in the buffer.
- **Changes**:
    - Add multiple slots to the buffer.
    - Maintain `fill_ptr` and `use_ptr` to track where to insert and retrieve items.
    - Adjust `put()` and `get()` routines:
```c++
void put(int value) {
    buffer[fill_ptr] = value;
    fill_ptr = (fill_ptr + 1) % MAX;
    count++;
}

int get() {
    int tmp = buffer[use_ptr];
    use_ptr = (use_ptr + 1) % MAX;
    count--;
    return tmp;
}
```
- **Updated Conditions**:
    - Producers wait only if all slots are filled (`count == MAX`).
    - Consumers wait only if all slots are empty (`count == 0`).
```c++
void *producer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == MAX)
            Pthread_cond_wait(&empty, &mutex);
        put(i);
        Pthread_cond_signal(&fill);
        Pthread_mutex_unlock(&mutex);
    }
}

void *consumer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == 0)
            Pthread_cond_wait(&fill, &mutex);
        int tmp = get();
        Pthread_cond_signal(&empty);
        Pthread_mutex_unlock(&mutex);
        printf("%d\n", tmp);
    }
}
```
### Key Concepts
- **Two Condition Variables**: Producers and consumers signal each other directly, avoiding unnecessary wakes.
- **Use `while` for Condition Checks**: Ensures correctness when state changes between a signal and execution.
- **Multi-threaded Web Servers**: Producers enqueue HTTP requests; consumers process them.
- **UNIX Pipes**: Producers write to pipes; consumers read from them.

## 30.3 Covering Conditions
- In multi-threaded programs, condition variables are used to synchronize threads waiting for specific conditions.
- A challenge arises when multiple threads wait for different conditions to be met, and a signal to wake a single thread may wake the wrong one.
### Example: Memory Allocation Library
- **Scenario**: A multi-threaded memory allocator manages a shared heap.
    - `allocate(size)` requests memory of a specific size.
    - `free(ptr, size)` releases memory and potentially wakes waiting threads.
- **Shared State**:
    - `bytesLeft`: Tracks free bytes in the heap.
    - `cond_t c` and `mutex_t m`: Used for synchronization.
```c++
int bytesLeft = MAX_HEAP_SIZE;
cond_t c;
mutex_t m;

void *allocate(int size) {
    Pthread_mutex_lock(&m);
    while (bytesLeft < size)
        Pthread_cond_wait(&c, &m);
    void *ptr = ...; // allocate memory
    bytesLeft -= size;
    Pthread_mutex_unlock(&m);
    return ptr;
}

void free(void *ptr, int size) {
    Pthread_mutex_lock(&m);
    bytesLeft += size;
    Pthread_cond_signal(&c); // whom to signal??
    Pthread_mutex_unlock(&m);
}
```
#### The Problem
- **Scenario**:
    - Thread **Ta** calls `allocate(100)` and waits because `bytesLeft < 100`.
    - Thread **Tb** calls `allocate(10)` and waits because `bytesLeft < 10`.
    - Thread **Tc** calls `free(50)`, freeing 50 bytes.
- **Issue**:
    - `pthread_cond_signal()` might wake the wrong thread, such as **Ta**, which still cannot proceed because `bytesLeft < 100`.
    - The correct thread (**Tb**) remains asleep, even though it can proceed with its smaller request.
#### Solution: Covering Conditions with Broadcast
- Replace `pthread_cond_signal()` with `pthread_cond_broadcast()`:
    - **Broadcast** wakes all threads waiting on the condition variable.
    - Each thread re-checks its condition and determines if it can proceed.
    - Threads that cannot proceed will return to sleep.
```c++
void free(void *ptr, int size) {
    Pthread_mutex_lock(&m);
    bytesLeft += size;
    Pthread_cond_broadcast(&c); // wake all waiting threads
    Pthread_mutex_unlock(&m);
}
```
### Advantages and Trade-offs
- **Advantages**:
    - Guarantees correctness: All threads are woken and allowed to re-check their conditions.
    - Prevents cases where the wrong thread is woken, avoiding deadlocks or missed progress.
- **Trade-offs**: Performance Overhead
	- Wakes all waiting threads, even those that cannot proceed.
	- Threads that cannot proceed will waste CPU cycles re-checking conditions and going back to sleep.
### Concept of Covering Conditions
- A **covering condition** is a conservative approach where all threads are woken to ensure correctness.
- In cases where it is difficult or impossible to determine which specific thread(s) should wake, a broadcast provides a simple, correct solution.
### Best Practices
- Use `pthread_cond_broadcast()` sparingly:
    - Only when it is challenging to wake the correct thread(s) efficiently.
    - Ensure correctness by re-checking conditions after waking (always use `while` instead of `if` for condition checks).
- **Alternative**: If a better design is possible (e.g., separate condition variables for distinct conditions), prefer that approach for efficiency.
### Real-World Applications
- **Memory Allocation**: Where threads request different sizes of memory and must wait for enough space.
- **Resource Management**: When multiple threads wait for different types of resources to become available.
