## 32.1 What Types Of Bugs Exist?
- **Concurrency Bugs**:
    - Issues that arise in multi-threaded or concurrent programs due to improper synchronization, resource sharing, or thread interactions.
    - Common in complex and mature codebases due to their scale and complexity.
### Study by Lu et al. 
- Analyzed concurrency bugs in four major open-source projects:
	1. **MySQL**: Database management system.
	2. **Apache**: Web server.
	3. **Mozilla**: Web browser.
	4. **OpenOffice**: Office suite.
- Focused on bugs found and fixed in these projects to provide insights into common concurrency issues.
#### Findings from the Study
- **105 Total Bugs**:
    - **Non-Deadlock Bugs**: 74
    - **Deadlock Bugs**: 31
- **Bug Distribution by Application**:
    - Mozilla: ~60 bugs.
    - Apache: ~30 bugs.
    - MySQL: ~7 bugs.
    - OpenOffice: ~8 bugs.

## 32.2 Non-Deadlock Bugs
- **Non-Deadlock Bugs**:    
    - Account for 70% of concurrency bugs studied by Lu et al.
    - Two major types:
        1. **Atomicity Violations**
        2. **Order Violations**
### Atomicity Violations
- **Definition**: Occurs when a sequence of operations intended to be atomic is interrupted, leading to incorrect results.
```c++
Thread 1::
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}

Thread 2::
thd->proc_info = NULL;
```
- **Problem**:
	- Thread 1 checks `proc_info` and finds it non-NULL.
	- Thread 1 is interrupted; Thread 2 sets `proc_info` to NULL.
	- Thread 1 resumes and dereferences a NULL pointer in `fputs()`, causing a crash.
- **Fix**: Use locks to ensure atomic access to shared resources.
```c++
pthread_mutex_t proc_info_lock = PTHREAD_MUTEX_INITIALIZER;

Thread 1::
pthread_mutex_lock(&proc_info_lock);
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}
pthread_mutex_unlock(&proc_info_lock);

Thread 2::
pthread_mutex_lock(&proc_info_lock);
thd->proc_info = NULL;
pthread_mutex_unlock(&proc_info_lock);
```
### Order Violations
- **Definition**: Occurs when the desired order between two (groups of) memory accesses is not enforced, resulting in incorrect behavior.
```c++
Thread 1::
void init() {
    mThread = PR_CreateThread(mMain, ...);
}

Thread 2::
void mMain(...) {
    mState = mThread->State;
}
```
- **Problem**:
	- If `Thread 2` runs before `Thread 1` has initialized `mThread`, it dereferences a NULL pointer, causing a crash.
- **Fix**: Use condition variables to enforce ordering.
```c++
pthread_mutex_t mtLock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t mtCond = PTHREAD_COND_INITIALIZER;
int mtInit = 0;

Thread 1::
void init() {
    mThread = PR_CreateThread(mMain, ...);

    pthread_mutex_lock(&mtLock);
    mtInit = 1;
    pthread_cond_signal(&mtCond);
    pthread_mutex_unlock(&mtLock);
}

Thread 2::
void mMain(...) {
    pthread_mutex_lock(&mtLock);
    while (mtInit == 0)
        pthread_cond_wait(&mtCond, &mtLock);
    pthread_mutex_unlock(&mtLock);

    mState = mThread->State;
}
```
### Patterns and Prevention
- **Atomicity Violations**:
    - Occur due to missing or incomplete locking.
    - Fix: Use locks to protect shared resources and ensure atomic operations.
- **Order Violations**:
    - Result from threads accessing resources in an incorrect sequence.
    - Fix: Use synchronization primitives like condition variables or semaphores to enforce proper order.
- **Key Insight**:
    - 97% of non-deadlock bugs are either atomicity or order violations.
    - Focus on these patterns can significantly improve concurrency safety.
### Lessons from Lu et al.
- **Automated Tools**: Should target atomicity and order violations to detect and prevent these bugs.
- **Best Practices**:
    - Always protect shared data with locks or synchronization primitives.
    - Use condition variables to enforce execution order when needed.
    - Test concurrency with stress tests to uncover hidden bugs.
- **Challenges**:
    - Fixes may require deeper understanding and significant refactoring in some cases.
    - Automated tools and careful design are critical to avoiding such bugs in practice.
